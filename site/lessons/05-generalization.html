Generalization

Part 1, Foundations. About 2 hours. No GPU needed. You'll leave with the habit that separates people who train models from people who fool themselves: never judge a model on the data it learned from.

Objectives

By the end of this lesson you can:

  1. Split data into training, validation and test sets, and say what each one is for.
  2. Produce overfitting on purpose and read it off two curves: training loss falling, validation loss rising.
  3. Stop training when the validation loss stops improving, and keep the best weights rather than the last.
  4. Apply weight decay and dropout, and explain what model.train() and model.eval() now change.
  5. Spot the two classic leaks: statistics fitted on all the data, and splitting without shuffling.

Where we are

Lesson 4 ended with a table where more parameters always meant lower loss, and a warning. Every loss in that table was measured on the deliveries the model trained on. Forkcast does not need a model that remembers past deliveries; it needs one that predicts the next one. This lesson is about measuring that, and about the three tools that improve it: more data, stopping in time, and regularization. It is the last lesson on synthetic data; from Lesson 6 the deliveries are real.

Three parts, three jobs

Shuffle the rows, then cut them into three. The training set is what gradient descent sees. The validation set is for decisions: which model size, when to stop, which learning rate; you look at it often, so it slowly leaks into your choices. The test set is for one honest number at the very end, looked at once. The shuffle is not optional. Data as stored is usually ordered by something, time or distance or customer, and cutting it in stored order gives you parts that differ from each other in exactly the way you are trying to measure.

def train_val_test_split(X, y, fractions=(0.7, 0.15, 0.15), seed=0):
    n = X.shape[0]
    perm = torch.randperm(n, generator=torch.Generator().manual_seed(seed))   # a random order of the row indices
    n_train, n_val = round(n * fractions[0]), round(n * fractions[1])
    idx_train, idx_val, idx_test = perm[:n_train], perm[n_train:n_train + n_val], perm[n_train + n_val:]
    return (X[idx_train], y[idx_train]), (X[idx_val], y[idx_val]), (X[idx_test], y[idx_test])

Overfitting

Give a 4545-parameter network 40 deliveries and let it train for 800 epochs. The training loss falls to 1, below the noise in the data, which should already worry you: the model is explaining noise. The validation loss falls with it for a while, reaches 8.0 around epoch 288, then climbs to 9.3. From that epoch on, every step made the model better at these 40 deliveries and worse at every other delivery. That is overfitting, and the distance between the two curves is the generalization gap. Dial it in yourself: fewer deliveries and more units make it worse; more deliveries, fewer units and weight decay make it better.

The dotted line in the left panel is the rule that generated the data. A good model ends up near it; an overfitted one wiggles through the training points instead. You will not have the dotted line for real data, which is why the validation curve on the right is the one you watch.

Early stopping

The validation curve has a minimum, and the model at that epoch is the best model you will get from this run. fit_with_validation evaluates after every epoch, keeps a copy of the weights whenever the validation loss improves, and, if you give it a patience, stops once the loss has gone patience epochs without improving. It then loads the best copy back into the model, so you get the model from the minimum, not the one from the end.

best_state = copy.deepcopy(model.state_dict())     # a snapshot: state_dict() alone is a live reference
for epoch in range(epochs):
    history["train"].append(train_one_epoch(model, X_tr, y_tr, optimizer, loss_fn))
    val_loss = evaluate(model, X_val, y_val, loss_fn)
    history["val"].append(val_loss)
    if val_loss < history["best_val"]:
        history["best_val"], history["best_epoch"] = val_loss, epoch
        best_state = copy.deepcopy(model.state_dict())
        since_best = 0
    else:
        since_best += 1
        if patience is not None and since_best >= patience:
            break
model.load_state_dict(best_state)

On the 40-delivery problem with patience=30, training stops after 319 epochs with the model from epoch 288, validation loss 8.0, instead of running to 800 and handing back 9.3. The deepcopy matters: state_dict() returns references to the live parameters, so without the copy your "best" weights would silently keep training.

Regularization

Early stopping limits how long a model can memorise. Regularization limits how easily it can. Weight decay adds a pull toward zero on every parameter each step, so the network must earn large weights with real signal; it is one argument to the optimizer. Dropout zeroes a random fraction of a layer's units on every training forward pass, so no unit can become indispensable and the network spreads what it knows. It is a layer, nn.Dropout(p), placed after the activation. And it is the first thing in this course that behaves differently in model.train() and model.eval(): random masks while training, nothing at all while evaluating. The toolkit has been switching modes since Lesson 3; now it matters.

MLP(4, (64, 64), dropout=0.2).net
Sequential(Linear(4, 64), ReLU(), Dropout(p=0.2), Linear(64, 64), ReLU(), Dropout(p=0.2), Linear(64, 1))

history = train.fit_with_validation(MLP(4, (64, 64), dropout=0.2), X_tr40, y_tr40, X_val, y_val,
                                    epochs=800, lr=0.01, weight_decay=1e-2)
history["best_val"], history["best_epoch"]         (5.81, 694)    the unregularized run bottomed out at 8.02
history["train"][-1]                               17.8   measured with dropout on: not comparable to the plain model's training loss

Two things to notice. The regularized model's validation loss is better than the plain model's ever was, with the same 40 deliveries. And its training loss looks terrible, because train_one_epoch measures it with the dropout masks active; judge regularized models by their validation loss only. The dropout noise also makes the validation curve bumpier, so give patience more room when dropout is on.

Leaks

A leak is anything that lets information from the validation or test set into training. Two happen constantly. Fitting the Normalizer on all the data before splitting: the test rows then shape the scaling the model trained with. The fix is the order of operations: split first, fit on the training part, transform the rest. And splitting without shuffling, as the widget above showed: on data sorted by distance, the test set is the twenty longest deliveries and the trained model scores a loss of 20 on it, three times its honest number, not because it is bad but because it was never shown anything like them.

Common errors

The "best" weights give the same loss as the last epoch
best_state = model.state_dict() without copy.deepcopy. The dictionary holds references to the live parameters, which kept training. Copy it.
Validation loss is suspiciously close to the training loss, or better
Some validation rows are in the training set, or the Normalizer was fitted on all the data, or you evaluated on the training tensors by mistake. Check the split sizes and the order of operations.
Validation loss jumps around wildly between epochs
Normal with dropout and a small validation set. Judge by the best value, not the last, and give patience more room.
Training loss is much higher than validation loss
Not a bug: the training loss was measured with dropout active. Compare models on validation loss only.
Test loss much worse than validation loss
Either the split was not shuffled, or you tuned so many choices on the validation set that it stopped being unseen. The test set exists to catch exactly this.
RuntimeError: Error(s) in loading state_dict: Missing key(s)
You saved a model with dropout and are loading into one without (or the reverse). The architectures must match, dropout layers included, because the layer positions in net shift.

Stretch

Repeat the overfitting experiment with five different torch.manual_seed values and plot all five validation curves; the best epoch moves, which is why early stopping is done per run and not by a fixed number. Then swap torch.optim.Adam for torch.optim.AdamW with the same weight_decay and compare: AdamW applies the decay directly to the weights instead of through the gradient, and for Adam-family optimizers it is the version that actually behaves like weight decay.
