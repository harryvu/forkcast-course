Where we are

Forkcast now has four models in four lessons' worth of files: minutes from order features, a dish from a photo, sentiment from a review, restaurants a customer will like. The capstone asks the question a product eventually asks: a new restaurant uploads a listing with a photo, a description and a price, and the app wants to know whether it will sell. The honest answer uses all three, and the capstone's job is to build the model that does, prove with an ablation that each input matters, and ship it the way Lesson 15 taught. The listings are synthetic so the tests run offline and so the signal can be planted on purpose; the notebook ends with pointers for doing the same on real data.

The task and the data

make_listings draws a photo (the Lesson 7 shapes, standing in for dish categories), a templated description whose words carry a portion and a freshness score, and three numbers: price, preparation minutes, rating. Demand is a weighted sum of all three plus noise, and the label is "above the median". By construction no single modality can get far: the image knows the category, the text knows the portion, the numbers know the price, and demand needs all of them.

Fusion: three encoders, one head

Each modality gets the encoder the course built for it, reduced to a vector of 32 numbers: the two convolutional blocks of Lesson 7 with a linear projection, Lesson 11's embedding with the masked mean, Lesson 4's MLP on the three standardized numbers. The three vectors are concatenated into 96 and a small head classifies them. This is late fusion, the simplest and most robust way to combine inputs, and it lets the model learn how much to trust each one. One design choice does the ablation for free: the model takes a modalities tuple, and an input that is not in it contributes a zero vector, so one class trains all seven combinations.

class FusionModel(nn.Module):
    def __init__(self, vocab_size, d=32, hidden=64, size=32, modalities=MODALITIES):
        super().__init__()
        self.modalities, self.d = tuple(modalities), d
        self.image_encoder = nn.Sequential(Conv2d(3, 16, 3, padding=1), BatchNorm2d(16), ReLU(), MaxPool2d(2),
                                           Conv2d(16, 32, 3, padding=1), BatchNorm2d(32), ReLU(), MaxPool2d(2), Flatten())
        self.image_proj = nn.Linear(32 * (size // 4) ** 2, d)
        self.text_embedding = nn.Embedding(vocab_size, d, padding_idx=0)
        self.tab_encoder = nn.Sequential(nn.Linear(3, d), nn.ReLU(), nn.Linear(d, d))
        self.head = nn.Sequential(nn.Linear(3 * d, hidden), nn.ReLU(), nn.Linear(hidden, 2))
    def forward(self, images, ids, mask, tabular):
        zeros = torch.zeros(images.shape[0], self.d, device=images.device)
        parts = [self.encode_image(images) if "image" in self.modalities else zeros,
                 self.encode_text(ids, mask) if "text" in self.modalities else zeros,
                 self.tab_encoder(tabular) if "tabular" in self.modalities else zeros]
        return self.head(torch.cat(parts, dim=1))                 # (N, 96) -> (N, 2)

Ablation: does every input earn its place?

Train the same model seven times, once per non-empty subset of modalities, with the same seed, data and budget, and compare validation accuracy. This is how you justify every input in a production model: an input that does not move the number is cost without benefit, and one that moves it a lot is where to invest in data quality. Measured in the sandbox, twelve epochs each:

combos = [c for r in range(1, 4) for c in itertools.combinations(MODALITIES, r)]
results = run_ablation(lambda m: FusionModel(len(vocab), modalities=m), train_loader, val_loader, combos, epochs=12, lr=2e-3)
image                    0.750
text                     0.715
tabular                  0.623
image + text             0.790
image + tabular          0.748
text + tabular           0.725
image + text + tabular   0.873

Every single modality is well above chance and well below the fused model, and the fused model beats the best pair by eight points. Had "tabular" come out equal to the fused result, you would have shipped a model without an image branch, and known why.

The model card

A model that ships without a model card is a model nobody can maintain. The card is a short Markdown file next to the artifact: what the model is for and what it is not for, what it was trained on, how it was evaluated and what the numbers were, where it is known to fail, and which code and lessons produced each part. write_model_card renders exactly those five sections; the content is yours to write, and writing it is where you discover what you do not know about your own model.

Common errors

RuntimeError: Sizes of tensors must match except in dimension 1 (torch.cat)
One encoder returned a different batch size or the zero vector has the wrong shape. Every part must be (N, d); build the zeros from images.shape[0].
TypeError: forward() takes 5 positional arguments but 2 were given
The collate returned a tuple that fit_v2 could not unpack as *inputs, target, usually because the label is not last.
The fused model is no better than tabular alone
Tabular inputs not standardized (see the break-it step), or a learning rate too low for the image branch to move in the epoch budget; the sandbox needed 12 epochs at 2e-3.
Ablation results are not comparable between runs
Different seeds or different epoch counts per variant. torch.manual_seed(0) before building each model, same loaders, same budget.
Reloaded model gives different predictions
The artifact is missing a constructor argument (modalities, d, size) or the vocabulary, so the rebuilt model has different shapes or different ids. Save everything the constructor and the encoding need.
Grad-CAM on the fused model is flat
Normal: the image branch carries part of the decision, and the heatmap shows only its part. Hook image_encoder[6] and compare an image-only variant to see the full-strength map.
