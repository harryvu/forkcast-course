Serving

Part 4, Shipping. About 2.5 hours. No GPU needed. You'll leave with Forkcast's three models behind one HTTP service that validates its inputs, answers in milliseconds, and runs from a single artifact file in a container.

Objectives

By the end of this lesson you can:

  1. Package a trained model with the preprocessing it depends on into one artifact, and load it with inference code only.
  2. Write an inference path that is correct (same features as training) and cheap (eval, inference_mode, batched).
  3. Export a model with torch.export and verify the exported program matches for any batch size.
  4. Expose /eta, /sentiment and /dish with FastAPI, with request validation and honest error codes.
  5. Measure p50 and p95 latency, explain the batching trade-off, and package the service in a Dockerfile.

Definition of done

Lesson 15 is done. Forkcast's models answer HTTP requests; the capstone puts them together.

Where we are

Everything so far ended in a notebook. Forkcast's app needs to ask, over HTTP, how long an order will take, what is in a photo, and whether a review is happy, and get an answer in a few milliseconds from a process that runs for months without a data scientist watching it. That is serving, and it has its own failure modes: the model gets different features than it trained on, a request arrives malformed, the service is too slow one order at a time, the weights file loads but nobody knows which run produced it. This lesson builds the service in the repository, tests it in-process with FastAPI's test client, and packages it in a Dockerfile.

The artifact: everything inference needs, nothing else

Lesson 3 saved a state_dict. A service needs more and less than that. More: the normalizer's mean and standard deviation, because the weights only mean something for inputs scaled the way training scaled them; the architecture sizes, to rebuild the same shapes; for text, the vocabulary; for classifiers, the class names; and a version, so a prediction can be traced to a run. Less: no optimizer state, no training data, no training code. The artifact must open with torch.load(path, weights_only=True) and nothing from the training side of the repository.

class EtaPredictor:
    def save(self, path):
        torch.save({"state_dict": self.model.state_dict(), "mean": self.normalizer.mean,
                    "std": self.normalizer.std, "hidden": list(self.hidden)}, path)         # 27 kB
    @classmethod
    def load(cls, path):
        bundle = torch.load(path, map_location="cpu", weights_only=True)
        model = TabularNet(4, zone_vocab=ZONE_VOCAB, hidden=tuple(bundle["hidden"]))
        model.load_state_dict(bundle["state_dict"])
        normalizer = Normalizer(); normalizer.mean, normalizer.std = bundle["mean"], bundle["std"]
        return cls(model, normalizer, tuple(bundle["hidden"]))

Inference: the training features, without the training machinery

The feature code at serving time must be the training code, not a re-implementation of it: the same column order, the same normalizer object, the same long ids. Build the batch from a DataFrame so the columns are looked up by name. Then model.eval() once at load, and torch.inference_mode() around every call: like no_grad but stronger, it skips the autograd bookkeeping entirely and the tensors it produces can never be used in a backward pass, which is what you want from a service.

def features(self, orders):
    frame = pd.DataFrame(orders)                                     # columns by name, never by position
    cont = torch.tensor(frame[CONTINUOUS].values, dtype=torch.float32)
    cat = torch.tensor(frame[CATEGORICAL].values, dtype=torch.long)
    return self.normalizer.transform(cont), cat

def predict(self, orders):
    with torch.inference_mode():
        return self.model(*self.features(orders)).tolist()           # plain floats: JSON cannot carry a tensor

eta.predict(orders[:3])                              [5.41, 13.49, 11.63]   minutes; batched and single calls agree to 1e-4

Export: a model without Python

torch.export traces the model into a graph of operations with fixed shapes, except the ones you declare dynamic, and saves it as a .pt2 file that loads without the model's class or any of your code. It is the route to runtimes that are not Python: mobile, C++, specialised inference servers. Declare the batch dimension dynamic, export with example inputs, and verify the loaded program agrees with the original for batch sizes you did not export with. ONNX is the other common target and follows the same shape: export, reload in the target runtime, compare outputs before trusting it.

batch = torch.export.Dim("batch")
program = torch.export.export(model.eval(), (cont[:4], cat[:4]), dynamic_shapes=({0: batch}, {0: batch}))
torch.export.save(program, "eta.pt2")                # 51 kB, no class definition needed to load
exported = torch.export.load("eta.pt2").module()
(exported(cont, cat) - model(cont, cat)).abs().max()  tensor(0.)   for batches of 1, 3 and 8

The API: validate first, then predict

FastAPI turns Python functions into HTTP endpoints and uses pydantic models to parse and validate request bodies before your code runs. A missing field, a string where a number belongs, a zone id of 999: all answered with status 422 and a message naming the field, and the model is never called. The endpoints return plain JSON; a model that is not loaded answers 503 rather than crashing; a request whose image has the wrong shape gets a 400 that says what shape was expected. Follow one request through.

class Order(BaseModel):

    pu_zone: int = Field(ge=0, lt=ZONE_VOCAB)
    do_zone: int = Field(ge=0, lt=ZONE_VOCAB)

Latency and batching

Measure, do not guess: time each call with perf_counter, repeat, and report percentiles. The median says what a typical request sees; the 95th percentile says what one in twenty sees, and that is the number users notice. On this CPU one order costs about 1 ms of model time, of which almost all is fixed overhead: sixty-four orders in one call cost 1.2 ms in total, 0.02 ms each. A service under load therefore collects the requests that arrive within a short window and runs them as one batch, trading a few milliseconds of waiting for fifty times the throughput.

latency_stats(lambda o: eta.predict([o]), orders, repeats=5)
{'p50_ms': 1.06, 'p95_ms': 1.27, 'mean_ms': 1.09, 'n': 40}      one order per call
latency_stats(lambda os: eta.predict(os), [orders * 8], repeats=5)["mean_ms"] / 64
0.019 ms per order                                               sixty-four per call
latency_stats(lambda o: client.post("/eta", json={"orders": [o]}), orders)["p50_ms"]
2.88 ms   the HTTP round trip in-process: parsing and validation cost more than the model

torch.set_num_threads matters in a service: PyTorch defaults to all cores, which fights the web server for them; half is a good start. And the Dockerfile in deploy/ installs the CPU build of torch, copies the package and the artifacts, and starts uvicorn deploy.app:app: the same service, anywhere Docker runs.

Questions

2. A forward pass costs 1 ms fixed plus 0.02 ms per order. How many ms does a batch of 32 orders take?

3. A client posts an order without trip_distance. What HTTP status does the service return?

4. Besides the weights and the hidden sizes, how many normalizer tensors does the ETA artifact store?

5. How many dimensions of the exported ETA program are dynamic?

6. The service was started without a sentiment model and a client posts to /sentiment. What status should it return?

Common errors

422 Unprocessable Entity, detail: loc ['query', 'request'], Field required
FastAPI did not recognise the pydantic class, usually because the models were defined inside a function under from __future__ import annotations, which turns annotations into strings. Define request models at module level.
Predictions are confident and wrong, status 200
The normalizer or the column order differs from training. Use the artifact's statistics and build features from a DataFrame by column name.
RuntimeError: Error(s) in loading state_dict: size mismatch
The artifact's hidden sizes were not used to rebuild the model. Read the config from the artifact, never from the training notebook.
torch.export raises on a data-dependent branch
The model has Python control flow that depends on tensor values. Rewrite it with tensor operations, or export a submodule; the course's models are export-friendly on purpose.
Exported program fails for a batch size other than the example's
The batch dimension was not declared dynamic. dynamic_shapes with a torch.export.Dim for dimension 0 of every input.
The service is slow under load though single requests are fast
One forward per request. Batch the requests arriving within a few milliseconds; and check torch.get_num_threads() is not fighting the server for cores.
