Experiment hygiene

Part 4, Shipping, optional. About 1.5 hours. No GPU needed. You'll leave with runs that reproduce to the last digit, a config that identifies each one, a log you can group and compare, and a rule for telling a real improvement from seed noise.

Objectives

By the end of this lesson you can:

  1. Seed every source of randomness in a run and say which one you cannot.
  2. Describe a run with a frozen config whose fingerprint changes when any field does, and round-trip it through JSON.
  3. Run an experiment from its config, reproducibly, and append the result to a JSON-lines log with the commit and the time.
  4. Group the log by configuration and read mean and spread across seeds.
  5. Decide whether a difference between two configs is real, and how many seeds it takes to know.

Where we are

Sixteen lessons of numbers: 5.44 against 15.43, 0.557 against 0.103, 0.873 against 0.750. Each was produced once in a sandbox, and the pages assert them. This lesson is about what gives a number like that the right to be believed: the run can be repeated and gives the same digits; the configuration that produced it is recorded, not remembered; the result sits in a log next to every other result, with the commit that produced it; and the comparison it supports was checked against the noise of the seed. None of this is PyTorch, exactly. All of it is the difference between an experiment and an anecdote.

Seeds: pin every source, know the one you cannot

A training run draws random numbers in half a dozen places: the initial weights, the loader's shuffle, dropout masks, the synthetic data or the split, any random or NumPy call in augmentation code, and the GPU's choice of kernels. torch.manual_seed covers torch's generators on the CPU and every GPU; Python's and NumPy's need their own calls; the DataLoader takes a seeded generator for its shuffle; and torch.use_deterministic_algorithms asks the GPU to prefer reproducible kernels, which some operations cannot provide. One function in the toolkit does all of it.

def seed_everything(seed, deterministic=True):
    random.seed(seed); np.random.seed(seed)
    torch.manual_seed(seed); torch.cuda.manual_seed_all(seed)
    torch.use_deterministic_algorithms(deterministic, warn_only=True)
    torch.backends.cudnn.benchmark = not deterministic           # benchmark picks kernels by timing: fast, and a source of drift
    return torch.Generator().manual_seed(seed)                   # for DataLoader(..., generator=g)

g = seed_everything(123); a = MLP(4, (8,)); g = seed_everything(123); b = MLP(4, (8,))
all(torch.equal(p, q) for p, q in zip(a.parameters(), b.parameters()))   True

Configs and fingerprints

Everything that decides a result belongs in one frozen object: model, sizes, learning rate, epochs, regularization, data size, data seed, seed. Frozen, so a run cannot quietly mutate it; a dataclass, so it has a name for every field; serialised to JSON, so it can be committed and read back; and hashed, so each distinct configuration has an eight-character fingerprint. Two runs with the same fingerprint must give the same digits; two with different fingerprints are different experiments, even if the only field that changed is the seed.

@dataclass(frozen=True)
class RunConfig:
    model: str = "mlp"; hidden: tuple = (32, 32); lr: float = 0.01; epochs: int = 150
    weight_decay: float = 0.0; dropout: float = 0.0; n_orders: int = 2000; data_seed: int = 0; seed: int = 0
    def fingerprint(self):
        return hashlib.sha256(json.dumps(asdict(self), sort_keys=True).encode()).hexdigest()[:8]

RunConfig().fingerprint(), replace(RunConfig(), lr=0.02).fingerprint()   ('1cf7a8b0', '108831ee')
RunConfig.from_json("run.json") == RunConfig()        True   tuples survive the trip

The log: one line per run, forever

run_experiment takes a config and does the whole run from it, seeding first, and returns a result that carries the fingerprint, the metric, the epoch it came from, the seconds it took, the git commit and the time, plus every config field. Appended as one JSON line to experiments.jsonl, the log is append-only, greppable and diff-friendly, and pandas reads it in one call. Grouping by every field except the seed turns a pile of runs into a table of configurations with a mean and a spread.

a = run_experiment(RunConfig(), "experiments.jsonl"); b = run_experiment(RunConfig(), "experiments.jsonl")
a["best_val"] == b["best_val"]                       True   7.5612 both times, 0.3 s each

Seed noise: is the difference real?

Run the same config under five seeds and the validation loss moves: 7.43 to 8.02 for the small network, a standard deviation of 0.24. That spread is the ruler for every comparison. The bigger network's mean is better by 0.84, more than three times the spread of a five-seed mean, so the improvement is real. Weight decay moved the mean by 0.02, a tenth of the spread: not an effect, a different seed. A single run per config cannot distinguish the two cases, and most "improvements" that vanish on rerun were exactly this.

Questions

1. How many libraries' random generators does seed_everything seed?

2. How many characters long is a config fingerprint?

3. Three seeds give best validation losses 7.1, 7.4 and 7.8. What is the mean, to two decimals?

4. What is the smallest number of runs that can show a config reproduces exactly?

5. Two configs differ by 0.1 in mean validation loss, and the std across seeds is 0.2. What is the ratio of difference to std?

6. RunConfig(seed=0) and RunConfig(seed=1): how many fields differ?

Common errors

Two runs with the same config give different digits
An unseeded source. Check in order: a DataLoader without generator, a random or NumPy call before seeding, data generated outside the seeded region, dropout with the model seeded after the data. On a GPU, non-deterministic kernels.
RuntimeError: … does not have a deterministic implementation
use_deterministic_algorithms(True) without warn_only=True turns an unavailable deterministic kernel into an error. The toolkit warns instead; read the warning, and know that operation is not pinned.
FrozenInstanceError: cannot assign to field 'seed'
The config is frozen on purpose. dataclasses.replace(cfg, seed=1) makes a new one.
from_json returns a config that is not equal to the original
JSON has no tuples: hidden came back as a list. Convert it on the way in.
compare() shows one row per run instead of per config
The seed, or a per-run field like seconds or timestamp, is in the group keys. Group by the configuration fields only, with hidden as a string so it is hashable.
The fingerprint changes between machines for the same config
Float formatting or key order in the JSON. sort_keys=True, and keep floats as plain Python floats, not NumPy scalars.
