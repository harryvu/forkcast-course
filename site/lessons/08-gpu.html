Where we are

The dish photos at the end of Lesson 7 took minutes on a GPU and would have taken an hour on the CPU, and the real Food-101 run in Lesson 9 is twenty times bigger. Training at that scale raises problems that had no reason to exist on four features: where the data lives, how precise the arithmetic needs to be, what happens when a Colab runtime disconnects at epoch 7 of 10, and how you know what the run is doing while you wait. This lesson solves each one once, inside the toolkit, so that the lessons after it only have to think about models.

The device: one variable, two kinds of move

A GPU is a separate computer with its own memory. Tensors live on one device or the other, and every operation needs all its inputs on the same one. The pattern is a single device variable chosen once, the model moved to it once, and every batch moved to it as it arrives. Two things differ. x.to(device) returns a copy: the original tensor stays where it was, so you write x = x.to(device). model.to(device) moves the module in place: its parameters change device, and the call also returns the module for convenience. Follow one training step across the two devices.

device = torch.device("cuda" if torch.cuda.is_available() else "cpu")   # forkcast.env.pick_device() since Lesson 0
torch.cuda.get_device_name(0)                        'Tesla T4'   or whatever Colab hands you
model = TabularNet(4).to(device)                     # parameters now on the GPU
for batch in loader:
    *inputs, target = batch
    inputs = [x.to(device, non_blocking=True) for x in inputs]   # copies; the CPU tensors are untouched
    target = target.to(device, non_blocking=True)
    ...
    total += loss.item() * len(target)                # .item(): the one moment the CPU waits for the GPU

Everything the toolkit does on the GPU is asynchronous: the CPU queues work and moves on. loss.item() is the exception, because a Python float needs the actual number, so the CPU waits there. Once per batch that is fine. Printing or .item()-ing inside the model's forward pass would make the GPU idle between every layer. torch.cuda.memory_allocated() tells you how much of the card you are using; running out of it is the most common GPU error, and a smaller batch_size is the usual fix.

Mixed precision: half the bytes, most of the speed

Parameters and activations have been float32 since Lesson 0: 32 bits per number. Modern GPUs multiply 16-bit numbers several times faster and move half as many bytes doing it. The catch is what 16 bits can hold. Look at what each format does to the kinds of numbers a training run produces.

Mixed precision means the parameters stay float32 and only the forward computations that are safe run in 16 bits. torch.autocast decides which ops those are, op by op, and casts on the way in; you wrap the forward pass in it and compute the loss outside, in float32. On a GPU the 16-bit type is float16, whose small range loses tiny gradients, so a GradScaler multiplies the loss by a large factor before backward(), divides the gradients back before the step, and skips the step when something overflowed. On a CPU autocast uses bfloat16, which has float32's range, and no scaler is needed; that is how the tests exercise this path without a GPU. The toolkit's make_scaler returns a scaler only where it helps.

with torch.autocast(device_type=device.type, dtype=autocast_dtype(device), enabled=amp):
    output = model(*inputs)                           # bfloat16 on CPU, float16 on CUDA
loss = loss_fn(output.float(), target)                # float32
if scaler is not None:
    scaler.scale(loss).backward(); scaler.step(optimizer); scaler.update()
else:
    loss.backward(); optimizer.step()

Augmentation: regularization made from data

A flipped photo of a dish is still a photo of that dish. So is one framed a little differently, or taken under warmer light. Applying such a random change every time an image is fetched means the network never sees the same tensor twice: it cannot memorise pixels, so it has to learn what makes a dish a dish. That is regularization, like dropout, but made from knowledge about the data: which changes keep the label true. It lives in the dataset's __getitem__, not in the model, and it is never applied to validation or test images.

from torchvision.transforms import v2
train_transform = v2.Compose([v2.RandomHorizontalFlip(), v2.RandomResizedCrop(32, scale=(0.7, 1.0), antialias=True),
                              v2.ColorJitter(brightness=0.2, contrast=0.2)])

class AugmentedTensorDataset(Dataset):
    def __getitem__(self, i):
        x = self.images[i]
        if self.transform is not None:
            x = self.transform(x)                     # a fresh random view on every fetch
        return x, self.labels[i]

200 training shapes, 15 epochs:   plain accuracy 0.865     augmented accuracy 0.940
1000 training shapes, 6 epochs:   plain accuracy 0.925     augmented accuracy 0.990

The gain is largest when data is scarce, which is exactly when you need it. The cost is CPU time per batch (0.45 s against 0.68 s per epoch here), which is what DataLoader's num_workers is for: the augmentation runs in worker processes while the GPU trains on the previous batch.

Checkpoints: a run you can resume

Lesson 3 saved a state_dict: the weights. That reloads a trained model; it does not let you continue training, because the optimizer has state too. Adam keeps running averages of every parameter's gradients, and a fresh Adam takes its first steps far too boldly. A checkpoint that resumes cleanly holds the model, the optimizer, the epoch number, the history so far and the best validation loss, all in one dictionary. Write it after every epoch; it costs a fraction of a second.

torch.save({"model": model.state_dict(), "optimizer": optimizer.state_dict(), "epoch": epoch,
            "history": history, "best_val": best_val}, "ckpt.pt")           # 65 kB for TabularNet

ckpt = torch.load("ckpt.pt", map_location=device, weights_only=True)      # map_location: a GPU checkpoint opens on a CPU
model.load_state_dict(ckpt["model"]); optimizer.load_state_dict(ckpt["optimizer"])
start = ckpt["epoch"] + 1

fit_v2(..., epochs=5, ckpt_path="full.pt")["train"]                         [292.68, 284.40, 280.76, 269.06, 259.47]
fit_v2(..., epochs=3, ckpt_path="r.pt"); fit_v2(..., epochs=5, ckpt_path="r.pt", resume=True)["train"]
                                                                             [292.68, 284.40, 280.76, 269.06, 259.47]   identical
# the same resume with only the weights restored:                      [292.68, 284.40, 280.76, 269.23, 260.49]   a different run

One more thing makes the resumed run identical rather than merely similar: fit_v2 seeds the random number generator with seed + epoch at the top of every epoch, so epoch 4's shuffle is the same whether or not the process restarted in between. Reproducibility is a design choice, and it is cheap when you make it early.

Logging, timing, and the free speedup

A history list is enough for a notebook; a run that takes an hour wants a live chart. SummaryWriter writes scalars to a directory that TensorBoard renders while training continues, and Colab can embed it with %tensorboard --logdir runs. fit_v2 also records seconds per epoch, which is the number to look at before anything else when a run feels slow: if the GPU is idle, the data loading is the problem, not the model. Finally, torch.compile(model) fuses the model's operations into faster kernels; it costs a slow first epoch and often buys back a third of the time after, which is worth it for long runs and not for short ones.

Common errors

RuntimeError: Expected all tensors to be on the same device, but found at least two devices, cuda:0 and cpu!
The model was moved and the batch was not, or the other way round. Remember x = x.to(device) for tensors; the toolkit's _split_batch does it for every element.
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate …
Halve batch_size. If it persists, turn on amp, or check for tensors kept alive by accident (a list of losses that are tensors rather than .item() floats is the classic).
Loss is nan with amp=True on the GPU but fine without
Float16 overflow in the forward pass, usually in a loss computed inside autocast. Compute the loss on output.float() outside the autocast block, and make sure the scaler is in use.
RuntimeError: Attempting to deserialize object on a CUDA device but torch.cuda.is_available() is False
A checkpoint written on a GPU, opened on a CPU, without map_location. Pass map_location=device.
Resumed run differs from the uninterrupted one
Optimizer state not restored, or the shuffle not seeded per epoch, or resume=True given without a ckpt_path that exists. All three are silent.
Validation accuracy is lower than training accuracy by a lot, and only with augmentation on
The augmentation was applied to the validation set too, or the transform is too aggressive (a 0.3 crop of a dish is a tablecloth). Validate on untouched images; tune the crop scale.
GPU utilisation near zero while training
The data loader is the bottleneck. Add num_workers, pin_memory=True, and move augmentation off the main process. epoch_seconds will show the difference.
