Tensors have shapes

A tensor is a grid of numbers with a shape. One number is a tensor with no dimensions. A list of numbers has one dimension. A table has two: rows and columns. Stack tables and you have three. PyTorch does not care what the dimensions mean, but you will, so this course colours them the same way everywhere:

  • batch size N: how many examples
  • features d: how many numbers describe one example
  • channels C and spatial H, W: for images
  • weights and outputs: arriving in Lesson 1

A Forkcast order might be described by four numbers: distance in km, number of items, hour of the day, whether it is raining. That order is a tensor of shape (4,). Thirty-two orders together are a tensor of shape (32, 4): one row per order, one column per feature. Try the presets, then type your own shape.

Two more properties travel with every tensor. The dtype is the kind of number inside; models want float32, and PyTorch gives you int64 when you build a tensor from whole numbers, which is the source of a classic error you will meet below. The device is where the numbers live: cpu, or cuda for a GPU. Tensors can only be combined with tensors on the same device.

import torch
torch.manual_seed(0)                  # same random numbers every run

orders = torch.randn(32, 4)           # 32 orders, 4 features, drawn at random
orders.shape                          torch.Size([32, 4])
orders.dtype                          torch.float32
orders.device                         device(type='cpu')

orders[0].shape                       torch.Size([4])      the first order
orders[:, 1].shape                    torch.Size([32])     the second feature of every order
orders[:3, :2].shape                  torch.Size([3, 2])   first three orders, first two features

torch.tensor([1, 2, 3]).dtype         torch.int64          whole numbers give int64
torch.tensor([1.0, 2.0, 3.0]).dtype   torch.float32        the dtype models use

Rearranging without changing the numbers

Most shape work is regrouping the same numbers. The six values of a (2, 3) tensor sit in memory as one line, 0 to 5. view and reshape cut that line into different groups; unsqueeze adds a dimension of size 1; permute is the odd one out because it changes the order you read the numbers in. Click each operation and watch the reading order.

Three of these you will use constantly: unsqueeze(0) turns one example into a batch of one, flatten(1) turns a batch of images into a batch of long vectors, and permute moves the channel dimension to where a library expects it.

one = orders[0]                        shape (4,)
one.unsqueeze(0).shape                 torch.Size([1, 4])          a batch of one order

images = torch.zeros(8, 1, 28, 28)     8 grayscale images
images.flatten(1).shape                torch.Size([8, 784])        keep dim 0, merge the rest
images.permute(0, 2, 3, 1).shape       torch.Size([8, 28, 28, 1])  channels last
images.reshape(8, -1).shape            torch.Size([8, 784])        -1 means "work this one out"

Broadcasting

Arithmetic between two tensors of different shapes is allowed when the shapes broadcast. The rule: line the two shapes up from the right. In each position the sizes must be equal, or one of them must be 1 (or missing). A size of 1 is stretched to match the other. You will rely on this in every lesson, usually to apply one number per feature to a whole batch, so it is worth being able to do it in your head.

The preset called the classic mistake is the one that will bite you first. A column mean computed with mean(dim=0) has shape (4,) and broadcasts fine. A per-order mean computed with mean(dim=1) has shape (32,) and does not; you need keepdim=True to get (32, 1).

bias = torch.tensor([0.0, 1.0, 2.0, 3.0])        shape (4,)
(orders + bias).shape                             torch.Size([32, 4])  bias stretched over 32 orders

col_means = orders.mean(dim=0)                    shape (4,)   one mean per feature
(orders - col_means).shape                        torch.Size([32, 4])

row_means = orders.mean(dim=1)                    shape (32,)  one mean per order
(orders - row_means).shape                        RuntimeError: The size of tensor a (4) must match
                                                  the size of tensor b (32) at non-singleton dimension 1
row_means = orders.mean(dim=1, keepdim=True)      shape (32, 1)
(orders - row_means).shape                        torch.Size([32, 4])

Common errors

You will see each of these more than once this course. Learn to recognise them by their first line.

RuntimeError: shape '[8, 700]' is invalid for input of size 6272
A reshape must keep exactly the same number of elements. Count them, or let PyTorch do it with -1 for one dimension: x.reshape(8, -1).
RuntimeError: The size of tensor a (4) must match the size of tensor b (32) at non-singleton dimension 1
Broadcasting failed. Line the shapes up from the right and find the pair that is neither equal nor 1. Usually the fix is keepdim=True on a reduction, or .unsqueeze(1) to turn (32,) into (32, 1).
RuntimeError: view size is not compatible with input tensor's size and stride (at least one dimension spans across two contiguous subspaces). Use .reshape(...) instead.
You called view after permute or transpose. Use reshape, which copies when it has to, or call .contiguous() first.
RuntimeError: Expected all tensors to be on the same device, but found at least two devices, cuda:0 and cpu!
One tensor moved to the GPU and another did not. Remember that .to(device) returns a new tensor: write x = x.to(device), not x.to(device) on a line by itself.
RuntimeError: expected scalar type Float but found Long
A tensor built from whole numbers is int64. Write 1.0 instead of 1, or convert with .float().
ModuleNotFoundError: No module named 'forkcast'
The notebook is not inside the repository folder, or the install cell did not run. Run %cd /content/forkcast-course and then !pip install -e . again.

A model is a function with knobs

A model takes an input and returns a prediction, using some numbers it can adjust. Ours has two: w, the minutes added per kilometre, and b, the minutes a delivery takes before the rider moves. In PyTorch they are 0-dimensional tensors, shape (), and the prediction for a batch of distances (N,) is one line of broadcasting:

pred = w * x + b          # () * (N,) + ()  ->  (N,)

Before any maths, do it by feel. Move the two knobs until the line goes through the cloud of deliveries.

Loss: one number for how wrong

You just judged the fit by eye. A program needs a number. For each delivery, the error is prediction − actual, positive when the model is too slow and negative when too fast. Squaring removes the sign and punishes big misses more than small ones; averaging gives one number for the whole batch. That number is the mean squared error, and making it small is the whole job.

errors = pred - y                       # (N,)  one error per delivery
loss = (errors ** 2).mean()              # ()    a single number
loss.item()                              740.5   as a plain Python float

Loss is a function of the knobs: change w and the loss changes. With b held fixed, that function is a curve, and it has a lowest point. Finding it is the next idea.

Gradient: which way is down

Stand on the loss curve at your current w. The ground has a slope. If it slopes up to the right, decrease w; if it slopes down to the right, increase it. The slope's steepness tells you how confident to be: steep means far from the bottom, flat means close. That slope is the gradient, and the rule move a little against the slope is gradient descent. How little is the learning rate.

Three things to notice. Steps shrink by themselves near the bottom, because the slope does. The learning rate is a trade: too small and you wait, too large and each step overshoots the valley and climbs the far wall, where the slope is steeper, so the next step is larger still. And nothing here knows what a delivery is: the same rule works for the millions of knobs in Lesson 9.

The two formulas

You need the slope of the loss with respect to each knob. Here is all the calculus this course asks of you. For one delivery with error e = w·x + b − y, the squared error e² has slope 2e with respect to e. When w grows by 1, e grows by x; when b grows by 1, e grows by 1. Multiply, then average over the batch:

e  = w * x + b - y                       # (N,)
dw = 2 * (e * x).mean()                  # ()  slope of the loss along w
db = 2 * e.mean()                        # ()  slope of the loss along b

w = w - lr * dw                          # one step downhill
b = b - lr * db

If the second formula feels like a special case of the first with x = 1, that is because it is: b is a weight on a feature that is always 1. Lesson 2 uses that trick, and then makes PyTorch derive both lines for you.

Where we are

Lesson 1's model knows one thing about a delivery: how far it is. Forkcast knows more: how many items are in the bag, whether it is raining, whether the order landed in the dinner rush. This lesson grows the model to use all four, and replaces the part of Lesson 1 that would not survive that growth: the hand-derived gradient formulas. With four weights you would need four formulas; with the networks of Lesson 4 you would need thousands. PyTorch derives them all, from the same code you use to make the prediction.

Autograd: PyTorch takes notes while you compute

Mark a tensor with requires_grad=True and PyTorch records every operation that touches it, building a graph from your inputs to your loss. Call loss.backward() and it walks that graph in reverse, applying the slope of each operation in turn, and deposits the result in each marked tensor's .grad. The slope rules it applies are exactly the ones you used in Lesson 1, which is why the numbers come out identical. Run this tiny example forward, then step backward one node at a time.

In code, the whole thing is three lines, and the model line is the one you already had:

w = torch.tensor(1.0, requires_grad=True)     # "please track slopes for me"
b = torch.tensor(2.0, requires_grad=True)

loss = ((w * x + b - y) ** 2).mean()           # forward: ordinary arithmetic, recorded
loss                                           tensor(389.1, grad_fn=<MeanBackward0>)
loss.backward()                                # backward: slopes flow to w.grad and b.grad
w.grad, b.grad                                 (tensor(-221.6), tensor(-36.7))   same as Lesson 1

Two details matter. .grad is None until the first backward(). And backward() needs a single number to start from: if you call it on the vector of errors instead of their mean, you get an error saying the gradient can only be created for scalar outputs.

Gradients add up until you zero them

Call backward() twice and .grad holds the sum of both slopes, not the latest one. This is deliberate: it lets large batches be split into pieces, which you will use in Lesson 13. In an ordinary training loop it is a trap. Every step must start from a clean .grad, so every step ends with w.grad.zero_(). Press backward a few times and watch; then look at what the same mistake does to a training run.

Forgetting to zero the gradient does not crash. The loss just stops making sense: it drops, jumps back up, drops again, because each step is pushed by every slope that came before. When you see a loss that bounces instead of settling, this is the first thing to check, before the learning rate.

From one feature to many

With four features, a prediction is four weights times four numbers, summed, plus b. For one order that is a dot product. For a batch of N orders stacked as rows of a (N, d) tensor X, it is N dot products at once, and PyTorch spells that X @ w. The shapes tell the story: (N, d) times (d,) gives (N,): the d is consumed, one prediction per order remains. Click each order to see its weighted sum.

The loop, version 2

Here is Lesson 1's fit with autograd doing the slopes and w grown to a vector. Three lines are new, and they are the three lines every PyTorch training loop has:

w = torch.zeros(4, requires_grad=True)
b = torch.zeros((), requires_grad=True)

for step in range(steps):
    loss = ((X @ w + b - y) ** 2).mean()
    loss.backward()                            # 1. slopes into w.grad and b.grad
    with torch.no_grad():                      # 2. the update is not part of the model
        w -= lr * w.grad
        b -= lr * b.grad
    w.grad.zero_()                             # 3. clean slate for the next step
    b.grad.zero_()

torch.no_grad() tells autograd to stop taking notes for the lines inside. Without it, the update itself would be recorded as part of the graph, and PyTorch refuses to modify a tracked leaf in place anyway. When the loop is done, return w.detach(): the same numbers, with the recording history cut off, which is what the rest of the program wants.

Common errors

RuntimeError: element 0 of tensors does not require grad and does not have a grad_fn
Nothing on the path to the loss had requires_grad=True, or you called .detach() too early. Check the two knob tensors.
RuntimeError: grad can be implicitly created only for scalar outputs
You called backward() on a tensor with more than one element, usually the errors instead of the loss. Add the .mean().
RuntimeError: a leaf Variable that requires grad is being used in an in-place operation.
The update w -= lr * w.grad is outside with torch.no_grad():. Indent it.
RuntimeError: Trying to backward through the graph a second time
You called backward() twice on the same loss tensor. The graph is freed after the first call. Recompute the loss before each backward(); a training loop does that naturally.
RuntimeError: mat1 and mat2 shapes cannot be multiplied (400x4 and 400x4)
The inner dimensions must match: (N, d) @ (d,). You multiplied X by something shaped like X, or forgot to transpose.
w.grad is None after backward()
The w you are looking at is not the one in the graph. w = w - lr * w.grad (without no_grad and without -=) creates a new, non-leaf tensor each step; gradients go to leaves only. Use the in-place update inside no_grad.
RuntimeError: Can't call numpy() on Tensor that requires grad. Use tensor.detach().numpy() instead.
Plotting a tensor that still carries autograd history. Do what the message says.

The model becomes an object

An nn.Module is a class that owns parameters and knows how to compute with them. You write two methods: __init__ creates the layers, forward says how input flows through them. Everything else, collecting the parameters for the optimizer, saving and loading, moving to a GPU, comes for free. The one layer you need today is nn.Linear, which is Lesson 2's X @ w + b as an object. Look at what it holds, and watch the shapes when the output grows.

from torch import nn

class LinearRegressor(nn.Module):
    def __init__(self, n_features):
        super().__init__()                        # always first: this is what registers the parameters
        self.linear = nn.Linear(n_features, 1)    # weight (1, d), bias (1,), random start

    def forward(self, X):                         # (N, d) -> (N,)
        return self.linear(X).squeeze(-1)         # nn.Linear gives (N, 1); y is (N,)

model = LinearRegressor(4)
model(X).shape                                    torch.Size([400])    calling the model runs forward()
model.linear.weight                               tensor([[-0.004, 0.268, -0.412, -0.368]], requires_grad=True)
sum(p.numel() for p in model.parameters())        5

That squeeze(-1) is the Lesson 1 silent bug, pre-empted. nn.Linear always returns a trailing dimension of size out_features, here 1. Compare a (400, 1) prediction with a (400,) target and broadcasting quietly builds a 400 by 400 table; nn.MSELoss at least warns you about it now. Squeeze, and the shapes agree.

The optimizer owns the update

In Lesson 2 the update was two lines inside no_grad, one per knob. An optimizer is handed model.parameters() once and applies the update rule to all of them on step(), and zeroes all their gradients on zero_grad(). Your loop shrinks to five lines, and the five lines are the same for a 5-parameter model and a 50-million-parameter one.

torch.optim.SGD is exactly Lesson 2's rule, w -= lr * w.grad. torch.optim.Adam keeps a running memory of each parameter's past gradients and scales its own step size per parameter; it is far more forgiving of a badly chosen learning rate and is the default choice for most of this course. Swapping one for the other is one word.

Why one learning rate kept failing

Distances run from 0.5 to 10, item counts from 1 to 6, and the rain flag is 0 or 1. The weight on distance feels every step a hundred times more strongly than the weight on rain, because the gradient for each weight is scaled by its feature's size. The loss is still a bowl, but a long narrow one: a step small enough to be safe along the steep direction crawls along the shallow one. Standardize every feature to mean 0 and standard deviation 1 and the bowl becomes round. Run both with the same learning rate.

class Normalizer:
    def fit(self, X):                               # learn the statistics from the training data
        self.mean = X.mean(dim=0)                   # (d,)
        self.std = X.std(dim=0, correction=0).clamp_min(1e-6)
        return self
    def transform(self, X):                         # apply the stored statistics to any data
        return (X - self.mean) / self.std           # Lesson 0's normalize_columns, made reusable

norm = Normalizer().fit(X)
norm.mean, norm.std                                 tensor([5.21, 3.52, 0.31, 0.25]), tensor([2.74, 1.71, 0.46, 0.43])
Xn = norm.transform(X)

Two rules. The statistics come from the training data and are then applied to validation and test data, never recomputed on them; Lesson 5 explains the leak that happens otherwise. And a model trained on normalized inputs expects normalized inputs forever: the Normalizer is part of the model, and ships with it in Lesson 15.

Definition of done

Where we are

The deliveries so far were made by a rule that is a straight line, so a straight line could learn it perfectly. Real deliveries are not like that. Rain does not add a fixed four minutes; it slows every kilometre. Past seven kilometres, Forkcast riders have to leave the main road for the bike-lane detour and the minutes climb faster. This lesson switches the generator to those rules with make_orders(nonlinear=True), watches the linear model fail, and builds the first model that can bend.

Where a line fails, and how to see it

Fit Lesson 3's LinearRegressor to the new deliveries and the loss stops at about 15, far above the noise floor of 4. The loss number says the model is missing something; a residual plot says what. Subtract actual minutes from predicted minutes and plot the difference against distance. A model that has captured everything leaves a shapeless band around zero. This one does not.

This plot is the most useful diagnostic you will own. Any time a loss plateaus above where you think it should, plot the residuals against each feature. A trend means there is a pattern left to learn and the model cannot express it.

Bending the line

A hidden layer is an nn.Linear whose outputs are not the answer. With one input and H hidden units it computes H different lines of the input. Then an activation changes each one; the usual choice is ReLU, max(0, z), which clips negatives to zero and turns each line into a ramp: flat, then rising (or falling) from the point where its line crosses zero, its kink. The output layer is one more nn.Linear that adds the ramps up with its own weights. A sum of ramps is a bent line, with up to H bends, placed wherever the data needs them. Train one.

Now set the activation to none and train again. The fit is a straight line and stays one, with 1 unit or 16. That is the whole reason activations exist, and it is the next section.

Stacking layers

Two linear layers in a row compute W2 (W1 x + b1) + b2, which is (W2 W1) x + (W2 b1 + b2): a single matrix times x plus a single bias. However many linear layers you stack, the result is one linear layer with a lot of redundant parameters. The activation between them is what stops the collapse, because max(0, ·) is not a matrix. So the recipe for a network is Linear, activation, Linear, activation, Linear, with no activation after the last layer, since minutes can be any number and ReLU would forbid negatives.

class MLP(nn.Module):
    def __init__(self, n_features, hidden=(32, 32), activation=nn.ReLU):
        super().__init__()
        layers, width = [], n_features
        for h in hidden:
            layers.append(nn.Linear(width, h))      # (N, width) -> (N, h)
            layers.append(activation())             # the bend
            width = h
        layers.append(nn.Linear(width, 1))          # no activation after the output
        self.net = nn.Sequential(*layers)

    def forward(self, X):
        return self.net(X).squeeze(-1)

MLP(4, (32, 32)).net
Sequential(
  (0): Linear(in_features=4, out_features=32, bias=True)
  (1): ReLU()
  (2): Linear(in_features=32, out_features=32, bias=True)
  (3): ReLU()
  (4): Linear(in_features=32, out_features=1, bias=True)
)

nn.Sequential runs its children in order and is itself a module, so state_dict names the parameters net.0.weight, net.2.weight, net.4.weight: the ReLUs at positions 1 and 3 have nothing to save. The shapes chain: (N, 4) becomes (N, 32), stays (N, 32), becomes (N, 1), and the squeeze makes it (N,). Nothing else in the training loop changes: train.fit from Lesson 3 takes this model as it took the last one.

Capacity

Parameters are what a network has to bend with. Count them: a Linear(in, out) has in × out + out, and the total for 4 → 32 → 32 → 1 is 160 + 1056 + 33 = 1249, against the 5 of the straight line. Here is what the same recipe learns on the new deliveries at different widths, with Adam at lr = 0.01 for 300 epochs:

LinearRegressor         5 parameters    loss 15.43
MLP(4, (8,))           49 parameters    loss 24.44   too small to bend enough, and slow to train
MLP(4, (32,))         193 parameters    loss  7.16

MLP(4, (64, 64))     4545 parameters    loss  4.79   the noise floor is about 4

More capacity, lower loss, all the way down to the noise. That looks like a rule you can follow forever. It is not: these numbers are the loss on the data the model trained on, and Lesson 5 shows what happens to the loss on deliveries it has never seen when you keep turning capacity up.

Where we are

Lesson 4 ended with a table where more parameters always meant lower loss, and a warning. Every loss in that table was measured on the deliveries the model trained on. Forkcast does not need a model that remembers past deliveries; it needs one that predicts the next one. This lesson is about measuring that, and about the three tools that improve it: more data, stopping in time, and regularization. It is the last lesson on synthetic data; from Lesson 6 the deliveries are real.

Three parts, three jobs

Shuffle the rows, then cut them into three. The training set is what gradient descent sees. The validation set is for decisions: which model size, when to stop, which learning rate; you look at it often, so it slowly leaks into your choices. The test set is for one honest number at the very end, looked at once. The shuffle is not optional. Data as stored is usually ordered by something, time or distance or customer, and cutting it in stored order gives you parts that differ from each other in exactly the way you are trying to measure.

def train_val_test_split(X, y, fractions=(0.7, 0.15, 0.15), seed=0):
    n = X.shape[0]
    perm = torch.randperm(n, generator=torch.Generator().manual_seed(seed))   # a random order of the row indices
    n_train, n_val = round(n * fractions[0]), round(n * fractions[1])
    idx_train, idx_val, idx_test = perm[:n_train], perm[n_train:n_train + n_val], perm[n_train + n_val:]
    return (X[idx_train], y[idx_train]), (X[idx_val], y[idx_val]), (X[idx_test], y[idx_test])

Overfitting

Give a 4545-parameter network 40 deliveries and let it train for 800 epochs. The training loss falls to 1, below the noise in the data, which should already worry you: the model is explaining noise. The validation loss falls with it for a while, reaches 8.0 around epoch 288, then climbs to 9.3. From that epoch on, every step made the model better at these 40 deliveries and worse at every other delivery. That is overfitting, and the distance between the two curves is the generalization gap. Dial it in yourself: fewer deliveries and more units make it worse; more deliveries, fewer units and weight decay make it better.

The dotted line in the left panel is the rule that generated the data. A good model ends up near it; an overfitted one wiggles through the training points instead. You will not have the dotted line for real data, which is why the validation curve on the right is the one you watch.

Early stopping

The validation curve has a minimum, and the model at that epoch is the best model you will get from this run. fit_with_validation evaluates after every epoch, keeps a copy of the weights whenever the validation loss improves, and, if you give it a patience, stops once the loss has gone patience epochs without improving. It then loads the best copy back into the model, so you get the model from the minimum, not the one from the end.

best_state = copy.deepcopy(model.state_dict())     # a snapshot: state_dict() alone is a live reference
for epoch in range(epochs):
    history["train"].append(train_one_epoch(model, X_tr, y_tr, optimizer, loss_fn))
    val_loss = evaluate(model, X_val, y_val, loss_fn)
    history["val"].append(val_loss)
    if val_loss < history["best_val"]:
        history["best_val"], history["best_epoch"] = val_loss, epoch
        best_state = copy.deepcopy(model.state_dict())
        since_best = 0
    else:
        since_best += 1
        if patience is not None and since_best >= patience:
            break
model.load_state_dict(best_state)

On the 40-delivery problem with patience=30, training stops after 319 epochs with the model from epoch 288, validation loss 8.0, instead of running to 800 and handing back 9.3. The deepcopy matters: state_dict() returns references to the live parameters, so without the copy your "best" weights would silently keep training.

Regularization

Early stopping limits how long a model can memorise. Regularization limits how easily it can. Weight decay adds a pull toward zero on every parameter each step, so the network must earn large weights with real signal; it is one argument to the optimizer. Dropout zeroes a random fraction of a layer's units on every training forward pass, so no unit can become indispensable and the network spreads what it knows. It is a layer, nn.Dropout(p), placed after the activation. And it is the first thing in this course that behaves differently in model.train() and model.eval(): random masks while training, nothing at all while evaluating. The toolkit has been switching modes since Lesson 3; now it matters.

MLP(4, (64, 64), dropout=0.2).net

Two things to notice. The regularized model's validation loss is better than the plain model's ever was, with the same 40 deliveries. And its training loss looks terrible, because train_one_epoch measures it with the dropout masks active; judge regularized models by their validation loss only. The dropout noise also makes the validation curve bumpier, so give patience more room when dropout is on.

Leaks

A leak is anything that lets information from the validation or test set into training. Two happen constantly. Fitting the Normalizer on all the data before splitting: the test rows then shape the scaling the model trained with. The fix is the order of operations: split first, fit on the training part, transform the rest. And splitting without shuffling, as the widget above showed: on data sorted by distance, the test set is the twenty longest deliveries and the trained model scores a loss of 20 on it, three times its honest number, not because it is bad but because it was never shown anything like them.

Common errors

The "best" weights give the same loss as the last epoch
best_state = model.state_dict() without copy.deepcopy. The dictionary holds references to the live parameters, which kept training. Copy it.
Validation loss is suspiciously close to the training loss, or better
Some validation rows are in the training set, or the Normalizer was fitted on all the data, or you evaluated on the training tensors by mistake. Check the split sizes and the order of operations.
Validation loss jumps around wildly between epochs
Normal with dropout and a small validation set. Judge by the best value, not the last, and give patience more room.
Training loss is much higher than validation loss
Not a bug: the training loss was measured with dropout active. Compare models on validation loss only.
Test loss much worse than validation loss
Either the split was not shuffled, or you tuned so many choices on the validation set that it stopped being unseen. The test set exists to catch exactly this.
RuntimeError: Error(s) in loading state_dict: Missing key(s)
You saved a model with dropout and are loading into one without (or the reverse). The architectures must match, dropout layers included, because the layer positions in net shift.

Dataset: one item at a time

A Dataset is a class with two methods: __len__ says how many items there are, and __getitem__(i) returns item i. That is the whole contract, and it is what lets PyTorch batch anything, tables, images, text, the same way. For trips, an item is a tuple: the four continuous features, the two zone ids as int64, and the minutes. Convert the whole frame to tensors once in __init__, so __getitem__ is a plain index.

class TripsDataset(Dataset):
    def __init__(self, frame, normalizer=None):
        cont = torch.tensor(frame[CONTINUOUS].values, dtype=torch.float32)        # (N, 4)
        self.cont = normalizer.transform(cont) if normalizer is not None else cont
        self.cat = torch.tensor(frame[CATEGORICAL].values, dtype=torch.long)       # (N, 2): indices, so int64
        self.target = torch.tensor(frame[TARGET].values, dtype=torch.float32)       # (N,)
    def __len__(self):
        return len(self.target)
    def __getitem__(self, i):
        return self.cont[i], self.cat[i], self.target[i]

DataLoader: items become batches

A DataLoader wraps a dataset and hands out batches. Each epoch it decides an order of the indices (a fresh random one when shuffle=True), walks that order batch_size items at a time, fetches each item with __getitem__, and stacks the tuples field by field, so a batch of trips is a tuple of three tensors with a leading batch dimension. drop_last=True throws away the short final batch, which keeps every training step the same size; the validation loader keeps it, because every row must be scored. Mini-batches change the loop, a little

Until now one epoch was one gradient step on all the data. With a loader, one epoch is len(loader) steps, each on a batch. Each step's gradient is an estimate from 256 trips rather than the exact gradient over all 4095, so the loss curve gets noisier, and training gets much faster per pass through the data, because fifteen updates happen where one did. Beyond speed, there is no choice: a month of real trips is three million rows, and a step over all of them at once would not fit in memory.

The toolkit grows loader versions of its functions. train_one_epoch_loader loops over the batches, and inside the loop the five lines are the ones from Lesson 3. Two details: a batch is a tuple whose last element is the target, so *inputs, target = batch and model(*inputs) work for one input or two; and the epoch's loss is the mean over rows, not over batches, so each batch's loss is weighted by its size. A device argument moves each batch before use; it is "cpu" today and does nothing, and in Lesson 8 it is the only thing that changes.

def train_one_epoch_loader(model, loader, optimizer, loss_fn, device="cpu"):
    model.train()
    total, seen = 0.0, 0
    for batch in loader:
        *inputs, target = batch
        inputs, target = [x.to(device) for x in inputs], target.to(device)
        optimizer.zero_grad()
        loss = loss_fn(model(*inputs), target)
        loss.backward()
        optimizer.step()
        total += loss.item() * len(target)          # weighted: the last batch may be smaller
        seen += len(target)
    return total / seen

Embeddings: a learned table for categories

The honest way to feed a category to a model is one-hot: a vector of 266 zeros with a single 1. The first linear layer then multiplies that vector by a (266, 8) weight matrix, and multiplying a one-hot vector by a matrix simply selects one row of it. nn.Embedding(266, 8) is that matrix with the multiplication skipped: give it an index, get a row of 8 learned numbers. The rows are parameters like any other, trained by the same backward pass, so zones that affect trip time the same way drift toward similar rows, with nobody telling the model what an airport is.

class TabularNet(nn.Module):
    def __init__(self, n_continuous, zone_vocab=266, emb_dim=8, hidden=(64, 64)):
        super().__init__()
        self.pu = nn.Embedding(zone_vocab, emb_dim)       # weight (266, 8)
        self.do = nn.Embedding(zone_vocab, emb_dim)
        self.mlp = MLP(n_continuous + 2 * emb_dim, hidden) # Lesson 4's MLP, input width 4 + 8 + 8
    def forward(self, x_cont, x_cat):                     # (N, 4), (N, 2) int64 -> (N,)
        features = torch.cat([x_cont, self.pu(x_cat[:, 0]), self.do(x_cat[:, 1])], dim=1)   # (N, 20)
        return self.mlp(features)

Images are tensors with four dimensions

A colour image is three grids of numbers, one per channel, red, green and blue, each H rows by W columns. PyTorch stores a batch as (N, C, H, W): channels before height and width, which trips up everyone coming from image libraries that put channels last; Lesson 0's permute is the fix when you meet one. Pixel values arrive as integers 0 to 255 and are scaled to 0 to 1, then normalized per channel with the mean and standard deviation of the training set, the Normalizer idea with one mean per channel instead of one per column.

Convolution: a few weights, slid everywhere

A fully connected layer on a 32×32 colour image would need 3072 weights per output, and it would have to learn separately that an edge in the top-left corner and the same edge in the bottom-right are the same thing. A convolution uses a small kernel of weights, 3×3 here, and slides it across the image, computing a weighted sum at every position. The same nine weights everywhere: far fewer parameters, and a pattern is detected wherever it appears. Each kernel produces one output grid, a feature map; a layer with 16 output channels has 16 kernels. Slide one.

The output size follows from how many positions the kernel can occupy: floor((size + 2·padding − kernel) / stride) + 1. With a 3×3 kernel, padding=1 keeps the size and stride=2 halves it. You will compute this constantly, so it is the first exercise. In nn.Conv2d(in_channels, out_channels, kernel_size) the weight has shape (out, in, k, k): every kernel looks at all input channels at once, so a kernel in the second layer sees all 16 feature maps of the first.

Pooling, BatchNorm, and stacking blocks

Between convolutions, MaxPool2d(2) keeps the largest value in each 2×2 patch, halving height and width. It has no weights; it makes the network indifferent to a shift of a pixel and lets the next layer's 3×3 kernels cover a wider region of the original image. Stack conv, pool, conv, pool, and the receptive field grows: the first layer sees edges, the second sees corners and strokes made of edges, a third would see parts of shapes.

BatchNorm2d sits after each convolution and normalizes every channel's activations across the batch, then rescales them with two learned numbers per channel. It is the Normalizer idea applied inside the network, and it lets you train deeper networks with larger learning rates. Like dropout, it behaves differently in training (batch statistics) and evaluation (running averages), so the model.train()/model.eval() calls in the toolkit are now doing two jobs.

The network, shape by shape

class SmallCNN(nn.Module):
    def __init__(self, n_classes=4, size=32):
        super().__init__()
        self.features = nn.Sequential(
            nn.Conv2d(3, 16, kernel_size=3, padding=1), nn.BatchNorm2d(16), nn.ReLU(), nn.MaxPool2d(2),   # (N, 16, 16, 16)
            nn.Conv2d(16, 32, kernel_size=3, padding=1), nn.BatchNorm2d(32), nn.ReLU(), nn.MaxPool2d(2),  # (N, 32, 8, 8)
        )
        self.head = nn.Sequential(
            nn.Flatten(),                                        # (N, 32 * 8 * 8) = (N, 2048)
            nn.Linear(32 * (size // 4) ** 2, 64), nn.ReLU(),
            nn.Linear(64, n_classes),                            # (N, 4) logits
        )
    def forward(self, x):
        return self.head(self.features(x))

It is also why Flatten must come after the last pool and nowhere else.

Classification: logits, probabilities, loss

Until now the model produced one number, minutes, and the loss was a squared distance. A classifier produces one number per class, the logits, which can be any real values. softmax turns them into probabilities that sum to one; the predicted class is the argmax. The loss is cross-entropy: minus the log of the probability the model gave the true class. Right and confident costs almost nothing; wrong and confident costs a lot, with no upper limit. nn.CrossEntropyLoss takes the raw logits and integer labels and does the softmax inside, more accurately than you would by hand, which is why the model's last layer has no activation.

Accuracy is the fraction of correct argmax decisions. It is what you report; it is not what you train on, because it is flat almost everywhere: nudging a weight rarely flips a decision, so it has no useful gradient. Cross-entropy is the smooth stand-in whose gradient points toward higher accuracy. Keep both in view: loss for the optimizer, accuracy for you.

The device: one variable, two kinds of move

A GPU is a separate computer with its own memory. Tensors live on one device or the other, and every operation needs all its inputs on the same one. The pattern is a single device variable chosen once, the model moved to it once, and every batch moved to it as it arrives. Two things differ. x.to(device) returns a copy: the original tensor stays where it was, so you write x = x.to(device). model.to(device) moves the module in place: its parameters change device, and the call also returns the module for convenience. Follow one training step across the two devices.

device = torch.device("cuda" if torch.cuda.is_available() else "cpu")   # forkcast.env.pick_device() since Lesson 0
torch.cuda.get_device_name(0)                        'Tesla T4'   or whatever Colab hands you
model = TabularNet(4).to(device)                     # parameters now on the GPU
for batch in loader:
    *inputs, target = batch
    inputs = [x.to(device, non_blocking=True) for x in inputs]   # copies; the CPU tensors are untouched
    target = target.to(device, non_blocking=True)
    ...
    total += loss.item() * len(target)                # .item(): the one moment the CPU waits for the GPU

Everything the toolkit does on the GPU is asynchronous: the CPU queues work and moves on. loss.item() is the exception, because a Python float needs the actual number, so the CPU waits there. Once per batch that is fine. Printing or .item()-ing inside the model's forward pass would make the GPU idle between every layer. torch.cuda.memory_allocated() tells you how much of the card you are using; running out of it is the most common GPU error, and a smaller batch_size is the usual fix.

Mixed precision: half the bytes, most of the speed

Parameters and activations have been float32 since Lesson 0: 32 bits per number. Modern GPUs multiply 16-bit numbers several times faster and move half as many bytes doing it. The catch is what 16 bits can hold. Look at what each format does to the kinds of numbers a training run produces.

Mixed precision means the parameters stay float32 and only the forward computations that are safe run in 16 bits. torch.autocast decides which ops those are, op by op, and casts on the way in; you wrap the forward pass in it and compute the loss outside, in float32. On a GPU the 16-bit type is float16, whose small range loses tiny gradients, so a GradScaler multiplies the loss by a large factor before backward(), divides the gradients back before the step, and skips the step when something overflowed. On a CPU autocast uses bfloat16, which has float32's range, and no scaler is needed; that is how the tests exercise this path without a GPU. The toolkit's make_scaler returns a scaler only where it helps.

with torch.autocast(device_type=device.type, dtype=autocast_dtype(device), enabled=amp):
    output = model(*inputs)                           # bfloat16 on CPU, float16 on CUDA
loss = loss_fn(output.float(), target)                # float32
if scaler is not None:
    scaler.scale(loss).backward(); scaler.step(optimizer); scaler.update()
else:
    loss.backward(); optimizer.step()

Augmentation: regularization made from data

A flipped photo of a dish is still a photo of that dish. So is one framed a little differently, or taken under warmer light. Applying such a random change every time an image is fetched means the network never sees the same tensor twice: it cannot memorise pixels, so it has to learn what makes a dish a dish. That is regularization, like dropout, but made from knowledge about the data: which changes keep the label true. It lives in the dataset's __getitem__, not in the model, and it is never applied to validation or test images.

from torchvision.transforms import v2
train_transform = v2.Compose([v2.RandomHorizontalFlip(), v2.RandomResizedCrop(32, scale=(0.7, 1.0), antialias=True),
                              v2.ColorJitter(brightness=0.2, contrast=0.2)])

class AugmentedTensorDataset(Dataset):
    def __getitem__(self, i):
        x = self.images[i]
        if self.transform is not None:
            x = self.transform(x)                     # a fresh random view on every fetch
        return x, self.labels[i]

Checkpoints: a run you can resume

Lesson 3 saved a state_dict: the weights. That reloads a trained model; it does not let you continue training, because the optimizer has state too. Adam keeps running averages of every parameter's gradients, and a fresh Adam takes its first steps far too boldly. A checkpoint that resumes cleanly holds the model, the optimizer, the epoch number, the history so far and the best validation loss, all in one dictionary. Write it after every epoch; it costs a fraction of a second.

One more thing makes the resumed run identical rather than merely similar: fit_v2 seeds the random number generator with seed + epoch at the top of every epoch, so epoch 4's shuffle is the same whether or not the process restarted in between. Reproducibility is a design choice, and it is cheap when you make it early.

Logging, timing, and the free speedup

A history list is enough for a notebook; a run that takes an hour wants a live chart. SummaryWriter writes scalars to a directory that TensorBoard renders while training continues, and Colab can embed it with %tensorboard --logdir runs. fit_v2 also records seconds per epoch, which is the number to look at before anything else when a run feels slow: if the GPU is idle, the data loading is the problem, not the model. Finally, torch.compile(model) fuses the model's operations into faster kernels; it costs a slow first epoch and often buys back a third of the time after, which is worth it for long runs and not for short ones.

Borrowed eyes

torchvision.models ships architectures with weights trained on ImageNet, 1.3 million photos of a thousand everyday things. ResNet-18 is the small one: 11.7 million parameters in a stem, four stages of residual blocks, a global average pool and a 512-to-1000 linear head. The early stages respond to edges and textures, which are the same in any photograph; the late stages respond to object parts and whole objects, which are closer to ImageNet's categories. The split between "general" and "specific" is what decides what to freeze.

Freeze, replace the head, train

Three moves. requires_grad_(False) on every parameter: autograd stops tracking them, no gradients, no updates, no memory for them. Then replace model.fc with a new nn.Linear(512, n_classes); a new layer requires gradients by default, so it is the only thing that trains. Then the toolkit's fit_v2, unchanged. Since the backbone is frozen, its 512-d output for each image never changes, which allows a trick: run the backbone once over the whole dataset, cache the features, and train the head on them. Seconds instead of minutes, and you can try ten heads.

def build_transfer_model(n_classes, pretrained=True, trainable_blocks=0):
    model = models.resnet18(weights=models.ResNet18_Weights.DEFAULT if pretrained else None)
    freeze(model)                                              # every parameter: requires_grad_(False)
    model.fc = nn.Linear(model.fc.in_features, n_classes)      # 512 -> n_classes, trainable
    for name in ["layer4", "layer3", "layer2", "layer1"][:trainable_blocks]:
        getattr(model, name).requires_grad_(True)              # unfreeze from the top down
    return model

Fine-tuning with two learning rates

Once the head is good, unfreezing the top block, layer4, lets the network adapt its object-level features to dishes. Those weights are already good, so they should move gently, while the new head can still move fast. An optimizer accepts parameter groups, each with its own settings, and that is how both happen at once: the head at 1e-3, the backbone at 1e-4. Fine-tune everything at the head's rate and the pretrained features are overwritten in the first epoch, which the break-it step below will show you.

def param_groups(model, lr_head, lr_backbone):
    head = [p for n, p in model.named_parameters() if n.startswith("fc.") and p.requires_grad]
    backbone = [p for n, p in model.named_parameters() if not n.startswith("fc.") and p.requires_grad]
    return [{"params": head, "lr": lr_head}, {"params": backbone, "lr": lr_backbone}]

Evaluating honestly

Accuracy is one number and a hundred classes hide inside it. A confusion matrix counts, for every true class, what the model called it: rows are truth, columns are predictions, the diagonal is what went right. From it come per-class accuracy (diagonal over row sums), which shows the classes the model cannot do, and the most-confused pairs, which show you what to look at: two dishes that are visually near-identical, or two classes with mislabelled data. Top-k accuracy asks whether the truth is among the k highest logits; for near-twins like pho and ramen, top-5 is the number papers quote, and the gap between top-1 and top-5 says how often the model is close but not exact.

per_class_accuracy(cm)                               tensor (101,) : diagonal / row sums
most_confused(cm, k=5)                               [(true, predicted, count), ...]   the pairs worth a look
top_k_accuracy(logits, y, k=5)                       a float; always ≥ top-1

The backbone's learning rate is too high, or you fine-tune with model.train() on BatchNorm layers with tiny batches, which corrupts their running statistics. Lower the rate; consider keeping the backbone in eval mode while fine-tuning the top block.
ValueError: some parameters appear in more than one parameter group
param_groups put a parameter in both lists. Split on the name prefix fc. exactly, and skip frozen parameters.
RuntimeError: mat1 and mat2 shapes cannot be multiplied (64x512 and 2048x20)
The head was sized for a different backbone. ResNet-18 and -34 pool to 512; ResNet-50 and larger to 2048. Read model.fc.in_features instead of assuming.
Downloading the weights fails
Colab has internet; CI does not and must not. Tests use pretrained=False; if you wrote a test that needs the real weights, mark it slow.

Where we are

Lesson 9 left you with a dish classifier and an accuracy number. In Forkcast that number decides things: whether a restaurant's photo is flagged as mislabelled, whether a search by picture returns the right dishes. Before a model with 80% accuracy touches real users, you need to know what the other 20% looks like, whether it is spread evenly or piled onto two classes, whether the model is reading the dish or the plate, and whether its 95% is really 95%. None of these are in the loss curve. This lesson is the toolkit for finding them.

Look at the mistakes

Start with the most informative errors: the ones the model was sure about. Sort every wrong prediction by the softmax probability of the predicted class and look at the top of the list. A confident mistake is one of two things, a systematic blind spot in the model or a mislabelled image in the data, and a gallery of the top sixteen usually tells you which within a minute. Low-confidence mistakes are the model being honestly unsure; they are expected and less interesting.

def misclassified(logits, y, k=16):
    probs = torch.softmax(logits, dim=1)
    confidence, predicted = probs.max(dim=1)
    wrong = (predicted != y).nonzero().flatten()
    order = wrong[confidence[wrong].argsort(descending=True)][:k]
    return [(int(i), int(y[i]), int(predicted[i]), float(confidence[i])) for i in order]

picks = misclassified(logits, y, k=16)
plt.imshow(gallery(images, picks).permute(1, 2, 0))   # the sixteen pictures worth your attention

Class balance

Count the training labels. If pizza has 400 photos and laksa has 40, a model that never predicts laksa loses almost nothing on the training loss, and its 90% accuracy is mostly the common classes. The per-class accuracies from Lesson 9 will show it; the fix is to make rare mistakes expensive. CrossEntropyLoss(weight=w) multiplies each image's loss by its class's weight, and inverse-frequency weights, total divided by classes times count, give every class the same total say regardless of size.

counts = class_counts(train_labels, n_classes)       tensor([400, 350, 300,  80,  60,  40])
weights = class_weights(counts)                       tensor([0.5125, 0.5857, 0.6833, 2.5625, 3.4167, 5.1250])   count × weight = 205 for every class
loss_fn = nn.CrossEntropyLoss(weight=weights.to(device))

Hooks: reading a layer without editing the model

A forward hook is a function you attach to a layer; PyTorch calls it every time the layer runs, with the module, its inputs and its output. It is how you look at intermediate tensors in a model you did not write, including every pretrained backbone. Two rules: the output is a tensor still in the graph, so .detach() it if you only want to look, and remove the hook with the handle you were given, or it fires on every forward pass for the rest of the session.

def record_activation(model, layer, x):
    captured = {}
    def hook(module, inputs, output):
        captured["out"] = output.detach()
    handle = layer.register_forward_hook(hook)
    try:
        model(x)
    finally:
        handle.remove()
    return captured["out"]

record_activation(model, model.features[6], images).shape   torch.Size([8, 32, 16, 16])

Grad-CAM: where did it look?

Take the activations of a late convolutional layer, a stack of 32 grids of 16×16. For the class you care about, ask autograd how its score changes with each activation: one gradient per grid cell. Average those over the grid, and each channel gets a single weight: how much that channel's pattern supports the class. Weight the grids, add them up, keep the positive part, and you have a 16×16 heatmap over the image of the evidence the model used. On the synthetic shapes the heat sits on the shape: inside it averages 0.2 to 0.5, the background under 0.15. On dish photos it tells you whether the model found the food or the fork.

class GradCAM:
    def __init__(self, model, layer):
        self.model, self.activations = model, None
        self.handle = layer.register_forward_hook(self._capture)
    def _capture(self, module, inputs, output):
        self.activations = output                        # left in the graph, on purpose
    def __call__(self, x, class_idx=None):
        self.model.eval()
        with torch.enable_grad():
            x = x.clone().requires_grad_(True)           # works even when every parameter is frozen
            logits = self.model(x)
            if class_idx is None:
                class_idx = logits.argmax(dim=1)
            score = logits.gather(1, class_idx.view(-1, 1)).sum()
            grads, = torch.autograd.grad(score, self.activations)       # (N, 32, 16, 16)
        weights = grads.mean(dim=(2, 3), keepdim=True)                  # (N, 32, 1, 1)
        cam = torch.relu((weights * self.activations).sum(dim=1))       # (N, 16, 16)
        return (cam / cam.flatten(1).max(dim=1).values.clamp_min(1e-8)[:, None, None]).detach()
    def remove(self):
        self.handle.remove()

Ask for a different class and the map moves: cam(x, class_idx=...) shows what would have supported "circle" in a picture of a cross. On Lesson 9's ResNet, hook model.layer4; its grid is 7×7 for a 224×224 input, and upsampling it over the photo gives the familiar red blob.

Calibration: does 90% mean 90%?

A classifier's softmax looks like a probability. Whether it behaves like one is a separate, measurable question: among all predictions made with 90% confidence, were 90% right? Bin predictions by confidence, compute accuracy per bin, and plot it against the diagonal. The weighted average gap is the expected calibration error. Neural networks trained with cross-entropy are usually overconfident, and overconfidence is what hurts in a product: a 95% that is really 70% overrules the human who was right.

probs = torch.softmax(logits, dim=1)
expected_calibration_error(probs, y)                 0.077    Lesson 7's SmallCNN on the shapes: accuracy 0.925, mean confidence 0.86
conf, acc, count = reliability_bins(probs, y)
bin confidence  0.35  0.46  0.55  0.66  0.75  0.85  0.97
bin accuracy    0.50  0.45  0.46  0.92  0.92  0.96  1.00
count              2    11    26    24    51    68   218

Here the model is slightly underconfident in the middle bins and well calibrated at the top, which is fine. If the top bin had read 0.97 confidence and 0.80 accuracy, you would reach for the fixes: label smoothing during training, or temperature scaling, a single number fitted on the validation set that divides the logits before the softmax and does nothing to accuracy.

Common errors

RuntimeError: One of the differentiated Tensors appears to not have been used in the graph
The hooked layer did not run in this forward pass (wrong layer, or a model with branches), or you detached the activations in the hook. Grad-CAM needs them attached.
RuntimeError: element 0 of tensors does not require grad and does not have a grad_fn
Every parameter is frozen and the input does not require grad either, so nothing is in the graph. x.clone().requires_grad_(True) before the forward pass.
The heatmap is all zeros for some images
Normal for an untrained or unsure model: the ReLU removes negative evidence and nothing positive was left. On a trained model, check you asked for a class the model considers plausible.
Memory climbs with every forward pass
A hook that appends to a list and was never removed. Hooks outlive the cell that created them; remove them in a finally.
ECE is exactly 0 but the model is clearly bad
You passed logits instead of softmax probabilities, so every "confidence" landed in the same overflow bin, or n_bins is 1. Softmax first; ten bins.
RuntimeError: weight tensor should be defined either for all 4 classes or no classes
The weight vector's length does not match the number of logits. class_weights(class_counts(labels, n_classes)) with the right n_classes.
